## Mailing list: a new Object-ID-model design thread; a SQUAD (QUIC multicast) BoF for IETF 127

- **"Simplifying the Object ID Model and caching" — [[ian-swett|Swett]], Oct-22, ~9 replies.** Swett proposes **requiring Object IDs within a Group to be sequential from 0** (0, 1, 2, …) rather than letting publishers assign non-contiguous/semantic IDs. Rationale: a cache/relay could then know a Group is complete as soon as it sees End-of-Group, avoiding wasteful upstream FETCHes for a Subscribe-delivered track that is already cached; he argues encoding meaning into the Object ID (e.g. as a timestamp) saves minimal bytes while making MoQ "much more brittle." The thread split:
  - **In favour:** [[aman-sharma|Aman Sharma]] (it would let the WG drop the Prior Object ID Gap property; bespoke needs can define their own parameter) and [[luke-curley|Luke Curley]], who calls FETCH very hard to implement with multiple subgroups and/or ID gaps — an intentional gap forces a wasteful upstream FETCH-to-check even with zero loss — and recommends making **Prior Object ID required**, pushing logical offsets up to the application (relays see dense 0,1,2,3), and restructuring so FETCH needn't stitch subgroups (stream-per-subgroup, or each subgroup numbered from 0).
  - **Skeptical / counter-proposals:** Christian Huitema notes congestion-driven relay skips create gaps the mandate can't prevent (Sharma concedes it only removes *intentionally-unused* slots). [[mo-zanaty|Mo Zanaty]] argues Prior Object ID Gap already covers publisher gaps (maybe just make it required) and proposes a **"Mind the Gap" Mandatory Track Property** — publishers set it if a track can have gaps; relays treat tracks without it as *dense* and never waste FETCHes — plus moving all gap machinery into an **extension draft** so the core draft defines only dense-track behavior. [[suhas-nandakumar|Suhas Nandakumar]] pushes back hardest: gaps are first-class by design (§2.1.2), the known-exists/known-not-exists/unknown state model exists precisely because IDs aren't assumed dense, and **subgroups make non-sequential IDs the normal case** (scalable coding with base/enhancement layers, keyframe-vs-P/B priority partitioning); datagram loss and stream resets mean the transport can't enforce density anyway. His counter: let an **application opt into a dense-from-zero property via its catalog/profile** and build caches around it — the simplification only where it's safe.

## Spec / WG: no merges; a REDIRECT / relay-redirect issue cluster; the FORWARD→PAUSED rename

- **REQUEST_ERROR caching + propagation — [#1997](https://github.com/moq-wg/moq-transport/pull/1997)** (*"Specify caching and propagation of REQUEST_ERRORs"*, [[victor-vasiliev|vasilvv]], Oct-15; fixes [#1582](https://github.com/moq-wg/moq-transport/issues/1582)). Specifies how a relay caches and forwards upstream `REQUEST_ERROR`s. Vasiliev flags three open questions: whether to cache **permanent errors and redirects** (most cache-efficient, but a bad redirect then sticks forever), what the **cache key** is (track for ~99%, but FETCH may vary on other parameters), and whether **PUBLISH** needs different treatment.
- **Relay-redirect abuse surface — [#1999](https://github.com/moq-wg/moq-transport/issues/1999)** (*"Relay redirect should not be able to say to publish to different namespace"*, [[cullen-jennings|fluffy]], Oct-15) and **[#2000](https://github.com/moq-wg/moq-transport/issues/2000)** (*"Relay behavior for REDIRECT is underspecified"*, Michal Hosna, Oct-15). Jennings argues a relay must not be able to redirect a publisher onto a *different* namespace — "too ripe for abuse." Hosna notes #1997 refines *forwarding* a REDIRECT but leaves *following* one unspecified: if a relay follows a REDIRECT that changes the Full Track Name A→B, which key are objects cached under, and how does it interact with Malformed Tracks? He suggests a relay should be *required to forward* a name-changing REDIRECT rather than follow it, and questions what use case needs following at all.
